# 任务聚类算法调研

Type: research
Status: resolved

## Question

用户方向（2026-08-11，07 grilling 中提出）：**纯算法实现事件→任务聚类，LLM 只做辅助**（不承担归属判定）。本 ticket 产出算法事实，供 07 聚类策略与 09 规格整合使用。

场景约束：

- Trace（Windows/Electron）任务系统 V1：事件日志为内存环形缓冲，事件 = `{type:'app-switch', appName, exePath, pid, windowTitle, ts}`（L0，无 URL/工作区）；分析触发 = 静默期（≥5 条新事件 + 静默 ≥60s）。
- 任务量级：几十条；事件批：5-50 条。
- 本地优先（隐私铁律）：优先本地 embedding 模型（Ollama 可跑）与纯算法，不依赖云端 embedding API。
- LLM（本地或云端，可配置）只做辅助：标题生成、原因解释、置信度标注。

问题清单：

1. **在线/流式聚类**：把事件流归组到"任务"（应用组合 + 时间局部性语义）的可行算法——BIRCH、stream K-means、时间窗 + 应用相似度等，哪些适配"任务"语义？增量更新（新事件进已有簇）怎么做？
2. **Embedding 路线**：本地 embedding 模型（bge-small-zh / nomic-embed-text / qwen3-embedding 等）在 Ollama 的可用性与体积；对短文本（窗口标题/应用名）聚类是否有效；余弦相似度 + 阈值判定的可行性。
3. **密度聚类**（HDBSCAN/UMAP）对 V1 场景（在线增量、几十任务）是否过度？
4. **事件批跨任务切分**：一个静默期的事件批可能包含两个任务的活动（如查资料后回写代码）——纯算法怎么切分（时间间隙 / 应用切换密度 / 窗口标题相似度）？
5. **LLM 辅助边界**：只做标题/原因生成 vs 参与归属；"低置信度"标注的判定标准（算法置信度阈值）；LLM 辅助对可解释性（原因展示）的贡献方式。
6. **相关文献**：online clustering / stream clustering / task segmentation / activity recognition 的经典与近期论文（附链接）。
7. **成本与结论**：内存/CPU/模型体积评估，给出 V1 推荐的轻量方案与理由。

## Answer

- 结论：V1 用**两级流水线**——①段化（驻留段 + 时间间隙硬切分 + 相邻段应用重叠率软切分，文献共识纯超时不够）②增量簇归属（每任务维护加权质心摘要，余弦/Jaccard 阈值判定并入 vs 新建；置信度 = best/margin 双判据，低置信样本交用户裁决）。BIRCH/CluStream 只借鉴 CF 摘要 + 吸收阈值 + 时间衰减三个思想，不上完整流式算法。
- Embedding：本地 Ollama 可选 nomic-embed-text（274MB）/ bge-m3（1.2GB）/ qwen3-embedding-0.6b（639MB）；中文最轻选项 bge-small-zh-v1.5 仅 26-48MB（社区 tag）。embedding 只做标题相似度通道，缺失时纯 token 重叠降级，隐私铁律在极端情形下也成立。
- HDBSCAN/UMAP 对 V1 明确过度（批量算法无流式更新、50-100 维以上性能衰减、几十点无密度可言），留作离线重分析的远期选项；LLM 只做命名/解释/低置信说明，归属判定全在算法侧（业界共识：LLM 在聚类中的角色是 after-stage 标签生成 + 可选事后抽查，无决定权）。
- 直接先例：Swish（标题语义 + 切换时间局部性，~70% 任务准确率）、CAiSE 2023（共现矩阵余弦切分 + DenStream 在线分类 + tf-idf 解释，架构与 Trace V1 几乎一一对应）。
