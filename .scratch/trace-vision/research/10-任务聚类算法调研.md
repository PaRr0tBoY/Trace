# 任务聚类算法调研

Type: research
Status: resolved
日期：2026-08-11（调研时点）
供：issue 07（AI 建议引擎规格）、issue 09（整合愿景）
方向：**纯算法事件→任务聚类，LLM 只做辅助**（不承担归属判定）

场景约束（本调研的结论边界）：

- 事件 = `{type:'app-switch', appName, exePath, pid, windowTitle, ts}`（L0，无 URL/工作区/文件内容）；内存环形缓冲；分析在"静默期"触发（≥5 条新事件 + 静默 ≥60s 后跑一次）
- 任务量级：几十条；每次分析的事件批：5-50 条；增量场景（事件流不断进入，任务持续演化）
- 本地优先（隐私铁律）：优先本地 embedding（Ollama 可跑）与纯算法
- LLM（本地 Ollama / 云端 DeepSeek，OpenAI 兼容）只做辅助：标题生成、原因解释、置信度标注

## 1. 在线/流式聚类：事件流归组到"任务"的可行算法

### 1.1 直接相关的算法谱系

| 算法 | 年份 | 增量方式 | 是否要 k | 噪音处理 | 对"任务"语义的适配度 |
|---|---|---|---|---|---|
| **BIRCH** | 1996 | CF-tree（聚类特征树），单遍扫描，新点沿树下降并入最近 CF，超阈值则新建叶 | 否 | 差（CF 树无噪音概念） | 中：CF 摘要天然支持增量；但纯特征向量，不含时间衰减 |
| **CluStream** | 2003 | micro-cluster（微簇，CF + 时间戳）；新点在自适应半径内→吸收，否则新建；簇数固定，过期簇删除/最近两簇合并；金字塔快照支持不同时间尺度 | 否（q 个微簇固定） | 中 | 高：微簇摘要 + 时间衰减的"最新任务画像"模式与任务演化直接对应 |
| **DenStream** | 2006 | potential/outlier 微簇 + 衰减权重；新点并入最近的 p-簇或 o-簇，权重超阈值 o→p 升级；定期剪枝过期簇 | 否 | 强（明确区分 core/outlier） | 高：DBSCAN 的流式版，簇任意形状、噪音稳健，**已被桌面任务识别文献直接采用**（见 §4） |
| **Incremental DBSCAN** | 1998 | 插入/删除只影响受影响点的邻域；证明与批量 DBSCAN 结果一致 | 否 | 强 | 中：度量空间通用；实现偏数据仓库场景 |
| **StreamKM++** | 2012 | coreset merge-reduce 缓冲 | 是（k） | 弱 | 低：k 未知场景不友好 |
| **在线 k-means**（Cohen-Addad 2021） | 2021 | 每步维护 k 个中心，新点按最近中心分配 | 是（k） | 弱 | 低：k 要先验；理论 regret 界，工程上不必要 |
| **Charikar 增量聚类**（SICOMP 2004） | 2004 | 新点到现有簇中心距离 ≤ 半径界→并入，否则开新簇；簇数超 k 时合并两簇 | 是（k） | 弱 | 中：给出"并入 vs 新建"的形式化模型，与任务归属判定同构；但按中心距离，无时间维度 |

### 1.2 增量更新（新事件进已有簇）的标准做法

1. **簇摘要而非原始点**：CF（n, LS, SS）三元组足以算质心与半径，且可 O(1) 合并/更新——BIRCH 提出，CluStream 扩展为带时间戳的微簇。任务侧对应物：**每任务维护 {应用计数向量、标题 token 频次、最后活跃 ts、质心 embedding（如启用）}**，新事件只需更新计数与加权质心。
2. **吸收判定**：新点与最近簇中心距离 ≤ 阈值（BIRCH 的 T、CluStream 的自适应半径、DenStream 的 ε）→ 并入；否则新建簇。这正是"新事件归已有任务 vs 新任务"的判定骨架。
3. **时间衰减**：CluStream/DenStream 用指数衰减权重让旧簇"退场"；任务演化场景对应"任务活跃度衰减"（一段时间不活跃的任务降权/归档）。
4. **离线再聚类**：流式算法通常在线做摘要、离线（按需）在摘要上跑 k-means/层次聚类细化。V1 的"静默期分析"天然就是离线阶段——在线部分只需维护摘要。

### 1.3 哪个适配"任务"语义（相近应用组合 + 时间连续）

文献里最贴合的现成先例（§4 详述）：**Swish**（窗口按标题语义 + 切换时间局部性聚类，~70% 任务分类准确率）与 **van der Aa CAiSE 2023**（切分后任务向量用 **DenStream** 在线聚类 + tf-idf 解释）。结论：**任务 = 应用组合相似 + 时间邻近**的语义，用"分段 → 每段特征向量 → 增量簇（质心 + 阈值判定）"即可覆盖，不需要完整流式聚类算法；BIRCH/CluStream 的 CF 摘要思想值得借鉴，DenStream 提供噪音（无关浏览/临时切换）处理先例。

### 2.2 短文本（窗口标题/应用名）聚类有效性

- 短文本聚类是成熟方向：稀疏性使传统 BoW/LDA 失效，**现代做法 = sentence-embedding + 余弦相似度 + 经典聚类**；论文证据：embedding + K-Means/HAC（层次聚类）在短文本上显著优于 HDBSCAN/OPTICS/Leiden 等参数少方法（需配合 k 估计；该文还提出无标签评估指标 Cohesion Ratio = 簇内平均相似度 / 全局平均相似度，ρ>1 说明聚类有结构）——arXiv:2511.19350：https://arxiv.org/html/2511.19350v2
- 另一条实证：短文本聚类用 LLM embedding（all-MiniLM 384 维）+ GMM 效果最好，且**簇命名一致性**（人类 reviewer 或 ChatGPT）是衡量"簇是否可解释"的有效指标——arXiv:2405.07278：https://arxiv.org/html/2405.07278v2
- **针对 Trace 场景的直接先例**：Swish 用标题词（PLSI）语义聚类 + 切换矩阵时间聚类，4 小时真实数据 ~70% 任务归属准确率；TaskPredictor 用窗口标题词袋 + 朴素贝叶斯，去噪后 ~60% 准确率、设置信度阈值后 80%+ precision @ 10-20% coverage——说明**窗口标题（哪怕只到 L0 级）是任务识别的有效信号**。

### 2.3 余弦相似度 + 动态阈值的可行性

- 余弦相似度是 embedding 聚类的标准相似度（eigenspectrum 方法、HAC 等都直接在其上构造），且短文本 embedding 空间里负余弦少见，通常 clip 到 [0,1]——arXiv:2511.19350 同上。
- 阈值可行但**必须按模型标定**：中文词向量实验里最优余弦阈值 0.45-0.5，阈值过高簇太小、过低簇过并——https://www.mdpi.com/2076-3417/9/8/1578 。不同 embedding 模型相似度分布不同，动态阈值思路：用"与最近簇相似度 vs 与次近簇相似度的差值（margin）+ 绝对阈值"双判据，比单一绝对阈值稳健（对应 CluStream 的"自适应半径"思想）。
- 无 embedding 时的纯算法兜底：应用名 token 的 Jaccard/余弦 + 标题 token 重叠，完全本地零依赖，可作为 embedding 缺席时的默认路径。

## 3. 密度聚类（HDBSCAN/UMAP）对 V1 是否过度？

**结论：是，V1 明确不用；留作离线分析的远期选项。**

- HDBSCAN 是**批量算法**：无原生流式更新（作者在 issue 中说明流式需要维护最小生成树 + condense tree 重算；`approximate_predict` 存在但慢——30k 向量单核 ~330s，且非增量训练）：https://github.com/scikit-learn-contrib/hdbscan/issues/34 、https://github.com/scikit-learn-contrib/hdbscan/issues/521 、https://github.com/scikit-learn-contrib/hdbscan/issues/487
- **维度敏感**：官方 FAQ 明确"50-100 维以上性能显著下降"；embedding 384-4096 维远超此范围（除非先降维）——https://hdbscan.readthedocs.io/en/latest/faq.html
- **数据量门槛**：密度聚类靠"足够数据分离稠密区"（min_cluster_size/min_samples），5-50 点的事件批、几十个任务的场景没有密度可言——同上 FAQ。
- 实证：短文本 embedding 上 HDBSCAN/OPTICS/Leiden 全面不如"k 估计 + K-Means/HAC"——arXiv:2511.19350。
- UMAP 是**降维/可视化**工具不是聚类器，几十个点无降维必要，还引入随机性。
- 什么时候才值得：任务量上到数百、需要发现任意形状/非凸任务簇、且做全量历史离线重分析时（HDBSCAN 的层次结构对"任务再分裂/合并"分析有价值）。V1 之后若做"任务归档回顾"可再评估。

## 4. 事件批跨任务切分（task segmentation）

### 4.1 现有研究（桌面/移动任务切分）

|---|---|---|---|

### 4.2 对 Trace V1 的映射（L0 事件只有 app-switch）

一个静默期批 = 一串 `app-switch` 事件，天然可切成"驻留段"（每段的驻留时长 = 下一个事件的 ts 差）。纯算法切分信号按可用性排序：

1. **时间间隙**（主信号，最便宜）：段间间隔超阈值 → 切。但文献一致警告**纯超时不够**（SIGIR 2020：F1 从 0.89 掉到明显更低；用户 ADHD 多任务切换频繁，短间隙也会是任务边界）。
2. **应用组合相似度突变**（次信号）：相邻两段的应用集合/计数向量余弦相似度出现"局部极小值 + 相对深度超过阈值"→ 切（CAiSE 2023 的 contextual relatedness 思路，用全局共现矩阵算上下文关联度）。对 Trace 可简化为：相邻段 app 集合重叠率 < 阈值 → 切。
3. **驻留时长加权**（防抖）：<2-3s 的瞬时切换（切来切去、误触）不构成独立段或直接并入邻段——TaskPredictor 的 WDS 与 SIGIR 的 sequential/switch 特征同思路。
4. 标题相似度突变：L0 有 windowTitle 可用（app-switch 事件携带），可作为第 2 信号的补充（同一任务内的标题 token 重叠率高）。

"查资料 20 分钟回写代码"场景的判定：切分在**段级**做，之后每段独立做任务归属；代码段与代码任务质心相似 → 归回原任务（即使中间隔了查资料段），这天然解决"一个批含两个任务"——切分和聚类两级各管各的。

## 5. LLM 辅助边界

### 5.1 业界做法：LLM 在聚类系统里的位置

| 阶段 | 做法 | 来源 |
|---|---|---|
| 聚类前 | LLM 生成约束（must-link/cannot-link）或改善输入特征 | TACL 2023（Few-shot clustering：三阶段 before/during/after）；AAAI 2025（LLM 约束生成，置信度阈值 + 惩罚机制防错约束，查询量降 20x） |
| 聚类中 | LLM 评估簇质量（语义连贯 GOOD/BAD）迭代重聚类 | arXiv:2412.09049（Dial-In LLM：连贯性评估 97.5% 准确率） |
| 聚类后 | **LLM 生成描述性标签**（主流且已商用：OpenAlex、CiteSpace 都用 LLM 给簇起名）；LLM 事后修正归属（查询"这个归属对吗"） | arXiv:2511.02601；TACL 2023；arXiv:2412.09049（命名 94.4% 对齐人工） |

**关键共识**：LLM 承担的是**命名/解释/质量审查**，归属判定（哪个点进哪个簇）几乎都由算法完成——这与用户"AI 只做辅助"的方向一致。LLM 在归属上的唯一常见参与是**事后抽查修正**（post-correction），且要配合置信度门槛控制成本。

### 5.2 "低置信度"标注的常见做法

- **算法侧置信度**（所有成功先例都用这个，不依赖 LLM）：
  - 阈值判定天然产生置信度：`conf = 与最近任务相似度`，或更稳健的 `margin = 最近相似度 − 次近相似度`（归一化）。
  - 双阈值的"三区制"：`conf ≥ θ_high` → 高置信并入；`θ_low ≤ conf < θ_high` → 低置信（建议但标注"待确认"）；`conf < θ_low` → 新建任务候选。
  - 先例：TaskPredictor 低于阈值**不预测**（80% precision @ 10-20% coverage 的权衡）；Swish 语义模块置信度不足时回退时间模块。
- **LLM 侧标注**：只对低置信/边界样本调用 LLM（节省成本），让它描述"为什么这两个任务候选都说得通"（生成解释性文本，不改变归属判定）。
- **归属最终决定权**：用户确认/编辑/忽略（Trace 07 的铁律），低置信建议 = 更需要用户裁决的样本。

### 5.3 可解释性贡献

- 算法可解释（零 LLM）：任务 = 应用组合直方图 + 驻留时长 + 标题高频词（Swish 用簇关键词；CAiSE 2023 用 tf-idf 找簇的判别词做解释）。"最近 12 分钟持续编辑 X + 浏览 5 个相关页面"式理由可以直接由算法统计生成。
- LLM 增强可解释：给簇关键词/事件统计 → LLM 生成人类可读标题与自然语言理由（描述性标签优于特征词拼接——arXiv:2511.02601 定义了两者区别；2405.07278 验证 ChatGPT 命名与人类 reviewer 一致性好）。注意 2405.07278 的警示：LLM 命名可作辅助但**应保留关键词级证据**供用户核对（"top words" 作为黑盒标签的对照）。

## 7. 成本与 V1 推荐方案

### 7.1 成本评估

- **纯算法路径**（无 embedding）：内存 = 环形缓冲事件（K 级）+ 每任务摘要（应用计数向量几十维 × 几十任务），总 < 1MB；CPU = 每次静默期分析 O(批 × 任务) 的向量点积，微秒级。**零模型依赖，永远可用。**
- **本地 embedding 路径**：nomic-embed-text ~274MB 模型 + 数百 MB 常驻（Ollama 常驻进程）；bge-small-zh-v1.5 26-48MB 是中文场景最轻选项；qwen3-embedding-0.6b 639MB 为质量更好但体积 10 倍以上的选项。CPU 推理短文本毫秒级，5-50 条/批可批量一次调用，开销可忽略。**embedding 只影响标题相似度通道，可独立开关。**
- **LLM 辅助路径**：只在分析触发时调用（每次分析 1-2 次：标题 + 低置信解释），几百 token；本地 Ollama 免费，云端 DeepSeek 每次 < ¥0.01。**与事件量无关，只与分析频率挂钩。**
- HDBSCAN/UMAP：V1 不用（§3），无成本。

### 7.2 V1 推荐：两级流水线（分段 → 增量簇归属）

```
事件批（5-50 条 app-switch）
  → ① 段化：驻留段 = 相邻事件时间差；<2-3s 瞬时切换并入邻段（驻留时长加权）
          段间间隙 ≥ GAP（默认 ~8-10min，可配置）→ 硬切分
          间隙不足但相邻段应用集合重叠率 < 0.3（或标题 token 余弦 < 阈值）→ 软切分（低置信边界）
  → ② 每段 → 特征向量 v = {应用计数 TF 向量（可按驻留时长加权）, 标题 token 频次}
          可选：段内标题 concat 的 embedding（本地模型，缺失时纯算法兜底）
  → ③ 归属：对每个已有任务（摘要 = 加权质心 + 最后活跃 ts + 事件数）算余弦相似度
          best ≥ θ_high（≈0.75 起步，按 embedding 标定；纯算法路径用 Jaccard ≥ 0.5）→ 并入，更新质心（指数滑动平均）
          θ_low ≤ best < θ_high → 低置信并入建议（标记 pending，交 LLM 解释 + 用户裁决）
          best < θ_low → 新任务候选
  → ④ 维护：任务摘要带时间衰减（CluStream 式，λ 周级）；久未活跃任务降权/归档；用户确认/编辑/忽略回写为信号（后续可学阈值）
  → ⑤ 辅助：LLM 只对"新任务候选"与"低置信样本"生成标题/理由；置信度 = max(margin, best) 归一化
```

数据结构：每任务 `{id, appVec: Map<appKey, count|weighted>, titleTokens: Map<token, count>, centroidVec?, lastActiveTs, eventCount, userState: 'confirmed'|'suggested'|'ignored'}`；全局 `coOccur: Map<appPair, count>`（CAiSE 2023 的共现矩阵，供段间关联度与"overhead 应用"识别）。

### 7.3 理由

- 任务量几十、批 5-50 条 → **质心近邻 + 阈值**是量级匹配的算法；BIRCH/DenStream 的完整机制是为百万级流设计的，其可迁移部分只是"CF 摘要 + 吸收阈值 + 衰减"三个思想。
- 分段与归属分离，直接命中"查资料后回写代码"场景（段归段、段归任务，两个层级互不干扰）。
- 置信度天然来自算法（best/margin），LLM 只做命名与解释，符合用户"AI 无决定权"铁律。
- 全部可在无 embedding、无 LLM 时降级运行（隐私铁律的极端情形也成立）。

### 7.4 风险

1. **标题信号噪声**（ADHD 高频切换、标题含版本号/随机串）：靠驻留时长加权 + token 清洗（去数字/停用词）+ 应用向量为主、标题为辅缓解；标题 embedding 质量需实机标定。
2. **阈值标定难**：θ_high/θ_low 因 embedding 模型而异（文献：0.45-0.5 最优阈值因模型不同而变）。对策：启动默认保守（宁多低置信、不瞎并入），用户裁决回写后自适应微调。
3. **任务交错**（两个任务并行进行）：单段可能混杂；V1 接受"段为归属单位"的粒度限制，段内混杂靠低置信标注暴露给用户，不做段内再切分。
4. **embedding 服务不可用**（Ollama 未启动/模型未装）：必须静默降级到 token 重叠路径，不能阻塞分析流程。
5. **冷启动**：新装无历史，任务全部从"新任务候选"开始，前几次建议噪音大——低置信标注 + 用户确认可接受。
6. **LLM 生成标题可能漂移**（生成式标题与事实不符）：建议卡同时展示算法证据（应用直方图/高频词），LLM 文本仅作辅助说明（2405.07278 的 top-words 对照经验）。
