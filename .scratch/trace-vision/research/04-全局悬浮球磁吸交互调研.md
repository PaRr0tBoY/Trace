# 04 · 全局悬浮球磁吸交互调研（Windows/Electron）

> 为愿景 V2"右下角圆球跟随鼠标 + 左缘磁吸 + 吸附展开 + 移开弹回"提供 Windows/Electron 可行性事实。原设计假设 macOS，本文按 Windows 重新论证。
> 调研日期：2026-08-11。所有结论以来源 URL 为证，标注"推断"的条目为基于来源的推导，非直接事实。

---

## 1. 全局跟随实现方案

### 1.1 现成参考：CursorBuddy（最接近的直接案例）

[jasonkneen/CursorBuddy](https://github.com/jasonkneen/CursorBuddy/) 是开源的 Electron 光标跟随悬浮助手，与 V2 圆球高度同构：

- 320×80 透明无边框置顶 click-through 窗口；**主进程 60fps 轮询光标**，renderer 用阻尼弹簧物理（`response: 0.2`、`dampingFraction: 0.6`，从 SwiftUI 移植），rAF 每帧应用，位置经 IPC 传回 main 进程移动窗口。
- 多显示器：`screen.getDisplayNearestPoint()` 检测光标所在屏，显示器变化时重新广播 bounds。
- 另有独立 panel 窗口（透明、圆角、自定义拖拽区）用于展开内容——**"跟随的 overlay 窗口"与"展开的 panel 窗口"分离**，正是 Trace 可以抄的结构。

结论：Electron 主进程轮询 `screen.getCursorScreenPoint()` + 每帧 `setPosition` 是已被生产代码验证的路线，不存在原理性障碍。Trace 现有 16ms（≈62Hz）轮询频率与 CursorBuddy 的 60fps 一致。

### 1.2 逐帧 setPosition 的抖动/延迟事实

| 事实 | 来源 |
|---|---|
| **鼠标抬起时抖动（jitter on mouse up）** 只发生在"把 bounds 经 IPC 发给 renderer 而不真正 setPosition"的反模式：Electron 缓存 setBounds 调用直到 mouseup 才执行，窗口跳到倒数第二帧位置。**只要在 main 进程真正调用 setPosition，此 bug 不触发**。 | [electron/electron#17682](https://github.com/electron/electron/issues/17682) |
| 在 renderer 进程用同步 IPC 做窗口位置动画会阻塞 repaint、表现为"卡顿/跳帧"；维护者明确建议动画逻辑放 main 进程。 | [electron/electron#15776](https://github.com/electron/electron/issues/15776) |
| 窗口移动时每帧同步保存窗口状态（bounds 持久化）会造成明显性能问题，业界用 100ms debounce 解决。跟随期间**不要**做任何持久化。 | [usebruno/bruno PR #6771](https://github.com/usebruno/bruno/pull/6771)（解决其 #5203） |

设计推论：V2 的弹簧物理与 setPosition 都应放 main 进程（零 IPC 往返），renderer 只管球的内容与面板内部动画。这与 CursorBuddy 的"renderer 弹簧 + IPC"略有不同——CursorBuddy 那样做可行（60fps IPC 无状态小 payload 没问题），但 Trace 已有主进程 16ms 轮询，直接在 main 做一阶弹簧积分（约 10 行）更简单，还省一跳 IPC 延迟。

### 1.3 备选方案评估

| 方案 | 结论 | 依据 |
|---|---|---|
| **WH_MOUSE_LL 低层鼠标钩子**（事件驱动代替轮询） | **不推荐**。高回报率鼠标（8000Hz）下钩子走消息队列，会拖慢全系统（KVM 软件 deskflow 的已知顽疾）；钩子有 `LowLevelHooksTimeout`（Win10 1709+ 上限 1000ms），超时被**静默移除**且无法感知；回调必须在带消息循环的线程。轮询成本恒定、与鼠标回报率无关，反而更稳。 | [deskflow#9298](https://github.com/deskflow/deskflow/issues/9298)、[LowLevelMouseProc (MS Learn)](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelmouseproc)、[SO: WH_MOUSE_LL 导致延迟](https://stackoverflow.com/questions/58870956/why-are-low-level-mouse-hooks-causing-lag) |
| Raw Input API | 针对高回报率鼠标的输入读取方案，但 RIDEV_NOLEGACY 与游戏输入方案纠缠，且需消息窗口；对"获取光标位置"这一需求无增益（光标位置用 GetCursorPos/轮询即可）。 | [PH3 Blog: Windows Input](https://ph3at.github.io/posts/Windows-Input/) |
| **保持现有轮询**（`screen.getCursorScreenPoint`） | **推荐**。成本固定（62.5Hz 一次本地 Win32 调用），与鼠标回报率无关；背景窗口鼠标移动导致 CPU 上升是 Chromium 上游行为且量小。 | [electron/electron#35327](https://github.com/electron/electron/issues/35327)（背景 CPU 上升，上游 Chromium 行为） |
| 原生 Win32 tool window（WS_EX_NOACTIVATE/TOOLWINDOW/LAYERED 自绘） | 原生方式无 Chromium 开销，但意味着放弃 Electron 渲染层（球内容、数字角标、动画全要 GDI/自绘），与 Trace 的 React 技术栈断裂。仅当 Electron 方案实测掉帧才值得考虑。 | [electron/electron#8533](https://github.com/electron/electron/issues/8533)（DPI 历史背景） |

### 1.4 业界产品怎么做的

- **claude-overlay**（Windows）：frameless always-on-top 聊天窗，折叠成"拖拽 orb"（固定位置、不跟随光标），Win32 API 做 DPI awareness / 圆角 / 多显示器。orb 是**窗口折叠态**而非独立小窗。 [l8w8/claude-overlay](https://github.com/l8w8/claude-overlay)
- **Mins Bot**：悬浮 orb + 展开聊天面板，orb 固定。 [mins.io](https://mins.io/)
- **Jarvis orb**（Tkinter）：托盘边缘锚定 + 手动拖拽 pin + 显示器拔掉回退主屏 + 拖出屏幕 clamp 回 workArea——多显示器位置持久化的完整参考。 [cephalochromoscope.net 规格](https://cephalochromoscope.net/06c46949-fabd-4bdf-9dcd-0036c3da21ae)
- **CursorBuddy**：唯一做"跟随光标"的 Electron 案例（见 1.1）。
- **ClawMonitor**：click-through 系统栏，**主进程 120ms 轮询 getCursorScreenPoint、IPC 驱动面板开关**——与 Trace 现有架构（16ms 轮询 + panel:leave 判定）完全同模式，是验证过的工程路径。 [iSymbolic 博客](https://isymbolic-blog.vercel.app/blog/clawmonitor/)

macOS 侧（NSPanel 非激活面板）是原设计假设；Windows 无 NSPanel 等价物，非激活置顶 = WS_EX_TOPMOST + skipTaskbar + focusable:false，见 [Electron: custom-window-interactions](https://fossies.org/linux/electron/docs/tutorial/custom-window-interactions.md) 与 [SO: transparent click-through overlay](https://stackoverflow.com/questions/50142924/create-electron-transparent-window-ontop-but-clickable-below-programs)。

## 2. 与现有边缘窗口架构的关系

### 2.1 独立球窗口 vs 合并进现有 384px 窗口

**推荐：独立球窗口（约 40–64px），复用现有面板窗口做展开。** 依据：

- CursorBuddy 就是 overlay 窗口 + panel 窗口分离的结构（1.1）。
- claude-overlay 的"同一窗口折叠成 orb"在 Windows 上等价于**每帧 resize + move**，比纯 move 昂贵，且折叠/展开瞬间的 setBounds 动画会触发 1.2 的抖动风险面。
- 现有 384px 面板窗保持不动（视觉 blade 270px 与 detector window 逻辑零改动），球窗口独立移动；**展开时球窗口隐藏、面板窗口从球位置弹出**——两个窗口都在 main 的 z-order 管理下（同一 'screen-saver' 级别 + 同一置顶心跳），切换用 hide/show，避免两个 WS_EX_TOPMOST 窗口同屏竞争。
- 现有 detector window（click-through 兜底 surface）逻辑对球窗口同样适用：球的"外部 OS 拖入感知"仍由主进程光标轮询完成。

### 2.2 点击穿透与常驻跟随的冲突

- 球窗口**必须常态 `setIgnoreMouseEvents(true, {forward: true})` + `focusable: false`**：跟随状态拦截任何点击都不可接受（球随时在光标右下角，会挡住点击）。forward 选项在 Windows 有效，转发 mousemove 给 DOM 以维持 mouseenter/mouseleave 判定。 [BrowserWindow docs](https://www.electronjs.org/docs/latest/api/browser-window)、[electron/electron#1335](https://github.com/electron/electron/issues/1335)
- 穿透与跟随**不冲突**：主进程轮询走 Win32，与窗口是否穿透无关；穿透只影响 DOM 事件。ClawMonitor 已验证"click-through 窗口 + 主进程轮询"组合（1.4）。
- 交互全部经由展开的面板，球只做"显示器"（任务数角标）——避免穿透/非穿透状态切换时的点击竞态（切换瞬间的一次点击归属不确定，[electron#1335 的 ModeManager 讨论](https://github.com/electron/electron/issues/1335)）。
- 若未来需要球本体可交互（如悬停看详情），再引入"元素级穿透切换"模式（mouseenter 切 setIgnoreMouseEvents(false)），但 V2 不建议。

### 2.3 多显示器与 DPI

- 光标在哪个屏球跟到哪个屏：每帧用 `screen.getDisplayNearestPoint(cursor)` 取当前显示器 bounds，把目标锚点（光标右下角）clamp 进该屏 workArea；显示器变化（拔插）时重新广播 bounds——CursorBuddy 的既有模式（1.1）。
- **混合 DPI 是真实风险**：per-monitor DPI 感知下 setPosition/setSize 在 scaleFactor 不同的多屏环境历史上不可靠（electron#10862 汇集了多个版本的问题）。已知 workaround：先 `setPosition(display.bounds.x, display.bounds.y)` 到目标屏原点再设目标位置；`setBounds` 有时比 `setPosition` 稳定；setPosition 坐标是 DIP（CSS 像素），跨屏时目标坐标必须以**目标屏的 bounds** 为基准换算。 | [electron/electron#10862](https://github.com/electron/electron/issues/10862)、[electron/electron#10659](https://github.com/electron/electron/issues/10659)、[electron/electron#9560](https://github.com/electron/electron/issues/9560)
- 球尺寸建议用固定 DIP 尺寸（跨屏视觉一致、无需按 scaleFactor 缩放逻辑）；仅在非整数缩放屏上实测验证圆度（1px 取整误差在 <64px 窗口上可见，[#10659](https://github.com/electron/electron/issues/10659) 的取整问题）。
- 现有 384px 面板窗的 workArea/热区逻辑（hotZoneHeight 等）与球互不干扰：球在任意屏移动，面板只在左缘展开。

## 3. 磁吸动画渲染层

### 3.1 Framer Motion 的现成模式（DOM 级）

磁吸/吸附/弹回是 Framer Motion 生态的成熟模式，直接可抄：

- **距离→力**：`pull = (1 - dist / radius) * strength`，dist < radius 时把偏移量写入 `useMotionValue`，经 `useSpring(raw, {stiffness, damping, mass})` 输出到 transform。radius 100–200px，strength 0.3–0.5 是实践甜点；弹簧典型参数 `{stiffness: 160, damping: 16, mass: 0.1}`。 | [Select Codes: Magnet Snap Button](https://select.codes/components/magnet-snap-button)、[SmoothUI 教程](https://smoothui.dev/blog/building-magnetic-button)、[unlumen Magnetic Button](https://ui.unlumen.com/docs/ui/unlumen/magnetic-button)
- 只在 transform（x/y）上动画，保持 60fps；`prefers-reduced-motion` 与粗指针（触屏）自动降级是标配要求。
- 离开后的弹回 = spring 归零（`rawX.set(0)`），天然带过冲/回弹质感；吸附到左缘 = 目标从"光标右下角"切换为"左缘锚点"。

**重要边界**：以上是 DOM 元素磁吸（renderer 内 transform）。V2 的球是**窗口**，屏幕位置动画必须在 main 进程 setPosition。两条路线：

| 路线 | 做法 | 评价 |
|---|---|---|
| A. main 进程做弹簧物理 | 每 16ms tick 一阶弹簧积分（`v += (target-pos)*stiffness*dt; v *= damping; pos += v*dt`），直接 setPosition | 推荐。零 IPC，与现有轮询同循环；弹簧参数从 CursorBuddy 的 response/dampingFraction 或 Framer 文档换算 |
| B. renderer 弹簧 + IPC 同步 | CursorBuddy 模式：renderer 用 Framer `useSpring`，rAF 每帧把位置经 IPC 发回 main setPosition | 已验证可行；代价是一跳 IPC（~1–2ms）与"动画在 renderer、窗口在 main"的调试割裂 |

"吸附-展开"的**视觉连续性**（球滑到左缘→变成面板头）建议用 renderer 内 Framer 动画实现：球滑到锚点后，球窗口隐藏，面板窗口在同一锚点位置以面板尺寸出现，面板内部用 Framer 做展开过渡——窗口级只有一次 show/hide + setBounds 到位的操作，不做窗口级每帧动画（避免 1.2 抖动面）。

### 3.2 物理感的意图判定（与 Framer 无关的窗口级逻辑）

"吸附-展开"的触发判定（磁吸力达到阈值 → 展开）有现成模式可参考：

- **velocity-aware 意图判定**：floating-ui 的 `safePolygon` 用光标速度（px/ms）判断"有意停留 vs 快速路过"，替代固定延迟；Ruixen 给出具体档位：速度 <2px/ms 视为有意（50ms 延迟）、>10px/ms 视为路过（250ms 延迟）、中间 150ms；离开时**方向感知**：朝面板方向给 300ms 宽限、离开方向 50ms 关闭。 | [floating-ui safePolygon](https://floating-ui.com/docs/usehover#safepolygon)、[floating-ui PR #2284](https://github.com/floating-ui/floating-ui/pull/2284)、[Ruixen UI: dropdowns that respond to intent](https://ruixen.com/blog/dropdowns-that-respond-to-intent)
- Trace 现有 3px 滞回 × 120ms 停留判定即这类模式的简化版；V2 磁吸阶段用速度档位替代固定停留更贴合"越近吸力越强"的连续模型。

## 4. 已知坑

### 4.1 全屏应用层级

- **'screen-saver' 置顶对独占全屏（exclusive fullscreen）游戏无效**：electron alwaysOnTop 只作用于普通窗口层级；LoL 等游戏切独占全屏后 Electron 窗口直接不可见（borderless 才可见）。Discord 的游戏内 overlay 是独立原生应用实现的。 | [SO 70050564](https://stackoverflow.com/questions/70050564/set-browserwindow-always-on-top-even-if-other-apps-games-are-in-fullscreen-ele)、[Overwolf 文档：exclusive fullscreen 无法 overlay，需 borderless](https://dev.overwolf.com/ow-electron/guides/product-guidelines/app-screen-behavior/in-game-overlays)
- 现有 'screen-saver' 心跳对普通窗口/菜单/borderless 全屏够用（[electron#11830](https://github.com/electron/electron/issues/11830)：screen-saver 级别解决被其他应用工具栏菜单覆盖）。**V2 规格必须写明**：独占全屏场景球/面板不显示——平台限制，非 bug；现有 koffi 全屏检测可顺带检测独占全屏并隐藏球。

### 4.2 OLE 拖拽冲突

- 现有架构"拖拽期间暂停置顶心跳"是对的：拖拽幽灵（SysDragImage）是 `WS_EX_TOPMOST + WS_EX_LAYERED` 窗口，置顶窗口会压到它上面。球窗口同样必须遵循此约束（拖拽期间暂停心跳，必要时隐藏球）。
- **electron#51556：SysDragImage 泄漏**——拖到外部进程目标后拖拽幽灵矩形残留（WS_EX_TOPMOST 孤儿窗口）。官方在 Electron 37→41 之间修复；Trace 是 **Electron 34，处于该 bug 影响区间**，风险需登记（复现条件：startDrag 拖出到非 Electron 应用）。 | [electron/electron#51556](https://github.com/electron/electron/issues/51556)
- electron#7118：Windows 上 `startDrag` + preventDefault 会禁用"拖回自己应用内部"的能力。Trace 目前只拖出到外部应用，不受影响；但 V2 若出现"从面板拖回球/面板内部"的交互会踩中。 | [electron/electron#7118](https://github.com/electron/electron/issues/7118)

### 4.3 误触防护

- 磁吸展开用速度档位 + 方向感知宽限（3.2），参数（速度阈值、radius、strength）应进设置，默认值参考 3.1 甜点。
- 球跟随本身无"误触"问题（click-through，不拦截任何输入），误触只发生在"展开"判定上。

### 4.4 任务栏区域

- 球锚点必须用 `display.workArea`（而非 bounds）避让任务栏；光标在任务栏上时球仍跟随（任务栏也是屏幕的一部分），但**磁吸吸附点若落在任务栏区域（左缘垂直任务栏）需特殊处理**——现有架构已存在此约束（面板展开盖任务栏），V2 沿用即可，规格注明。
- 多显示器时每屏 workArea 独立（每屏任务栏位置可能不同），锚点按光标所在屏取。

### 4.5 光标消失（触屏/无鼠标/独占全屏）

- 触屏/笔输入时光标被系统抑制：`GetCursorInfo` 的 `CURSORINFO.flags` 返回 `CURSOR_SUPPRESSED`，位置仍可用但光标不可见。可用 koffi 调 GetCursorInfo 检测（Trace 已有 koffi 基建），检测到抑制 → 球退回"锚定模式"（固定右下角，不跟随），避免球停在无意义位置。 | [CURSORINFO (MS Learn)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-cursorinfo)、[SO: GetCursorInfo 返回 NULL 句柄（无物理鼠标）](https://stackoverflow.com/questions/58437626/windows-function-getcursorinfo-returns-success-but-the-handle-to-the-cursor-is)
- 设备级检测：`GetSystemMetrics(SM_TABLETPC)` / `SM_DIGITIZER` 判断触屏/笔设备存在。 | [GetSystemMetrics (MS Learn)](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getsystemmetrics)
- 远程桌面/多输入桌面：GetCursorPos 只返回当前输入桌面位置（Win10 后自动跟随活动桌面），远程会话下跟随行为按实际光标走即可，无额外处理。
- 独占全屏游戏场景光标被隐藏但位置仍在 → 配合 4.1 的全屏检测一起隐藏球。

### 4.6 其他

- 现有 16ms 轮询在 renderer 无 DOM 事件（click-through）的前提下成本固定；不要为"省电"降低轮询频率而引入跟随延迟（CursorBuddy 60fps 是同类产品的基准）。
- 两个置顶窗口（球 + 面板）同屏时：同一 'screen-saver' 级别下后创建的压先创建的，展开流程必须是"隐藏球 → 显示面板"严格串行，避免闪烁。

## 5. 推荐实现路径 + 风险清单

### 推荐路径（供规格 V2 章节采用）

1. **新增加球窗口**（独立 BrowserWindow，~48–64px，frameless / transparent / skipTaskbar / focusable:false / 常态 click-through with forward）。不并入现有 384px 面板窗。
2. **main 进程弹簧物理**（路线 A）：现有 16ms 轮询循环里，每 tick 计算光标右下角锚点 → clamp 进光标所在屏 workArea（`getDisplayNearestPoint`）→ 一阶弹簧积分 → `setPosition`。磁吸半径/强度/弹簧参数进设置。
3. **展开状态机**：速度档位判定（有意停留 vs 路过）→ 球被吸向左缘锚点（弹簧目标切换）→ 球窗口隐藏、面板窗口在锚点弹出（内部展开动画用 Framer Motion 在 renderer 做）→ 移开后面板收回、球窗口恢复、弹簧目标切回右下角弹回。
4. **复用现有约束**：置顶心跳（含 OLE 拖拽暂停）覆盖球窗口；koffi 全屏检测扩展到独占全屏 → 隐藏球；`GetCursorInfo` CURSOR_SUPPRESSED 检测 → 球退回锚定模式。
5. **混合 DPI 防御**：跨屏移动用"先到目标屏原点再设目标"的 workaround；上线前在 100%/125%/150% 混合屏实机验证。

### 风险清单

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| 1 | 独占全屏游戏下置顶无效（平台限制） | 已知/接受 | 规格明写；koffi 全屏检测顺带处理，球隐藏 |
| 2 | 混合 DPI 屏 setPosition 偏移（electron#10862 系） | 中 | 目标屏原点先落位 workaround；实机矩阵验证 |
| 3 | Electron 34 处于 SysDragImage 泄漏影响区间（#51556） | 中 | 登记；验证复现，必要时升 Electron 或启动期清理孤儿窗口 |
| 4 | 每帧 setPosition 在低端机上的成本 | 低 | main 进程内做、零 IPC；62.5Hz 与 OS 拖窗频率同级 |
| 5 | 球/面板两窗口 z-order 切换闪烁 | 低 | hide/show 严格串行，同 level + 同一心跳 |
| 6 | 误触展开（路过左缘误开面板） | 低 | velocity 档位 + 方向感知宽限，参数可调 |
| 7 | 触屏/无鼠标设备球停在不合理位置 | 低 | CURSOR_SUPPRESSED 检测 → 锚定模式 |
