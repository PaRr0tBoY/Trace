## Answer

### 决议（2026-08-11 grilling，用户逐项确认 + 一项自定义转向）

**1. Screenpipe 集成后置（用户转向）**

- V1 不集成 screenpipe。用户方向：后续再调研竞品，或学习 screenpipe 的事件驱动采集逻辑（事件触发捕获、debounce、结构化事件类型、保留策略）用于自研。
- 02 调研保留作架构参考（`research/02-screenpipe深度调研.md`）；许可风险随之消解（V1 无第三方集成）。

**2. 实时事件：自建 koffi 轮询 L0**

- main 进程每 500ms 轮询 GetForegroundWindow（koffi：GetWindowTextW / GetWindowThreadProcessId / QueryFullProcessImageNameW，沿用全屏检测基建），前台窗口变化时生成事件。
- 事件结构（借鉴 screenpipe ui_events 的字段设计，V1 只做 app-switch 级）：`{ type: 'app-switch', appName, exePath, pid, windowTitle, ts }`
- 数据流：L0 事件 → 事件总线 → 任务归属器（按 AppRef 匹配，更新 lastActiveAt 与状态机，01 语义）+ 事件日志（内存环形缓冲，上限 1000 条，不持久化；07 建议引擎的输入）。
- 不做 SetWinEventHook（毫秒级收益对 15 分钟状态机阈值无感，复杂度高）。

**3. 生命周期管理（随 screenpipe 后置消解）**

- 无第三方进程托管需求；自建轮询随 Trace 主进程生命周期。

**4. 隐私护栏：分级开关 + incognito 联动**

- 设置"任务采集"区：①任务系统总开关 ②L0 前台事件采集开关（默认开；只记录应用名/窗口标题/PID，不含内容）③L3 内容理解开关（默认关、按需授权——V1 无实现，规格预留）。
- Trace 现有 incognito 开启时暂停 L0 事件记录。
- 窗口标题可能含敏感文件名——L0 开关即护栏，规格注明。

**5. 性能预算**

- 500ms 轮询一次 Win32 调用，成本可忽略；无第二常驻进程。

**6. 依赖**

- 06（事件接入任务/剪贴板关联交互）、07（事件批消费）、09（规格整合）。
