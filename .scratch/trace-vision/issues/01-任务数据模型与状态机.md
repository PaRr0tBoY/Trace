# 任务数据模型与状态机

Type: grilling
Status: resolved

## Answer

### 决议（2026-08-11 grilling 两轮，用户逐项确认）

**1. 存储**：独立 TaskStore，`tasks.json`（userData，与 items.json 同模式，带 version 字段），无新依赖；剪贴板存储完全不动。

**2. Task 模型（V1）**

```ts
type TaskStatus = 'active' | 'paused' | 'waiting' | 'completed'

interface AppRef {
  id: string // 应用身份 key：exePath 小写归一化，无则进程名
  name: string // 显示名（如 "Code" / "chrome"）
  exePath?: string
  lastContext?: { // 最新上下文快照（L1 采集的落点，见 05）
    windowTitle?: string
    url?: string // 浏览器
    workspace?: string // 编辑器
    cwd?: string // 终端
  }
}

type ResourceRef =
  | { kind: 'clipboard'; itemId: string; snapshot: { type: ItemKind; preview: string; capturedAt: number } }
  | { kind: 'files'; paths: string[] }

interface Task {
  id: string // t_ 前缀
  title: string
  status: TaskStatus
  note?: string // 临时想法
  apps: AppRef[] // 多对多；同一应用可属多任务；按 id 去重，lastContext 取最新
  resources: ResourceRef[] // 多对多（item 可属多任务）；快照兜底
  createdAt: number
  updatedAt: number
  lastActiveAt: number // 状态机时间基准
}
```

- 无 priority/color（后加 JSON 字段成本极低）；无任务数上限（V1 由用户管理）；无回收站（删除 = 硬删 + 确认）。

**3. 状态机（规则驱动，AI 不猜）**

- Active ↔ Paused：无归属事件超过阈值（默认 15 分钟，设置项可配 1-120 分钟）→ Paused；收到归属事件 → Active（或 Paused 恢复）。
- 事件归属：前台应用/窗口/URL 匹配任务 AppRef → 该任务收到归属事件（lastActiveAt 更新）；多任务共享同一应用时"最近活跃优先"，不强行打断；归属判定实现归 05/07，模型层只定义 lastActiveAt 语义。
- 多个任务可同时 Active（用户真实并行切换时不互斥）。
- Waiting / Completed 仅用户手动；Waiting → Active 用户手动恢复；Completed 保留在已完成分组（可恢复为 Active、可删除 = 硬删 + 确认）。
- 用户可手动暂停（Active → Paused）。

**4. AI 建议（suggestion）**

- 瞬态、内存驻留、不持久化（重启丢弃）；确认后 → 匹配现有任务则 merge（并入 apps/resources/时间戳，TaskStore 定义类型安全 merge 操作），无匹配则新建；"是否匹配"的判定归 07；[忽略] 只丢弃本次建议。

**5. 排序与展示**

- 状态分组（Active > Waiting > Paused > Completed），组内 lastActiveAt 降序；球上数字 = Paused + Waiting 数（不含 Active/Completed）。

**6. 边界与依赖**

- 反向查找（item → 任务）V1 用扫描（任务量小），不做索引。
- IPC 推送：新增 state:tasks（TaskDto 全量推送，与 state:items 同模式）；走四文件合约。
- 依赖：05（归属事件流 / 上下文快照来源）、06（关联交互细节）、07（匹配/聚类判定）。
