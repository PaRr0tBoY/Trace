## Design Context

### Users

- **Primary**: the developer (Acid), power user, uses the panel dozens of times per day as its own clipboard manager. Also ships to a small user base of clipboard-heavy desktop users (designers, developers, writers).
- **Context**: always-on-top edge blade on Windows. Zero-click interaction — hover to open, click/paste/drag to use. Sessions are short and frequent (open → act → leave, seconds at a time).

### Brand Personality

- 暗黑精密机械感 (dark precision-mechanical): calm, restrained, fast, zero-noise. Animations behave like precision instruments — crisp damping, a hint of spring, never showy.
- References: BoringNotch / Apple Dynamic Island (overshoot-and-settle, content stays still while the shape moves), mechanical audio haptics (dial ticks, toggle snaps — already in soundEffects.ts).
- Anti-references: bouncy/elastic easings, confetti, glassmorphism glow, anything that draws attention to the animation itself.

### Aesthetic Direction

- Pure black (#000) surfaces, thin 1px white-ish dividers, one accent color (themeable). Typography-driven, no card-in-card nesting.
- Motion: compositor-only (transform + opacity + promoted clip-path). 60fps on 4K. Fast entrances (≤300ms), subtle micro-feedback (≤200ms), exits faster than entrances (~75%).
- Reduced motion is an **app-level choice** (two levels: standard/extended), NOT tied to the OS "Show animations" flag — the OS flag on the author's machine silently killed all animation once; the app must never do that again. Default = standard.

### Design Principles

1. **Motion communicates state, not decoration.** Every animation answers "what changed?" (opened, copied, pinned, selected, new content arrived). If it doesn't, it doesn't exist.
2. **The shape moves, content stays.** Follow BoringNotch: animate the container/background shape; never scale or slide content that carries information (text, lists).
3. **Fast is default.** Feedback ≤200ms, state changes ≤300ms, entrances ≤500ms. Exit = 75% of enter. One well-orchestrated reveal beats scattered micro-motion.
4. **Performance is a hard constraint.** Only transform/opacity/promoted clip-path. Gate expensive effects by item count (12-card enter limit, 30-card FLIP limit). Infinite loops + drop-shadow filters are the known jank source — keep them off or gated.
5. **The user owns the motion level.** standard = crisp functional motion (reveal, card enter/exit, flyouts, toasts, hover); extended = standard + delight (open bounce, tab-capsule spring, view slide, new-item highlight, empty-state entrance, badge pops, press feedback, copy ripple, indicator breathing). OS prefers-reduced-motion is ignored by design (documented in useOpenBounce); the in-app setting is the single source of truth.

### Mechanism Notes (verified 2026-08-14, framer-motion 11.18.2)

- `MotionConfig reducedMotion="always"` only snaps **positional keys** (transform family + width/height/top/left/right/bottom) — **opacity springs survive it** (verified: opacity 0.74 mid-flight under "always"). The two-level refactor deleted the minimal level and with it `MotionGlobalConfig.skipAnimations` — `reducedMotion="never"` stays pinned (explicit: OS flag never consulted).
- One source, per-mechanism gates: `settings.motionLevel` → CSS `data-motion` (extended-only rules under `:root[data-motion='extended']`, e.g. .act press scale) · Framer per-component `=== 'extended'` checks (bounce values, capsule spring vs 0.14s tween, flash, badge, ripple) · GSAP own gates (LiquidOctopusLoader, CopyIndicatorCurve icon breathing). `useAdaptiveSpring`/`useSubtleSpring` are DPR-only now (no motionLevel branch).
- Card enter animations are un-staggered (user rejected stagger as invisible); enter is a uniform 0.3s spring per card, capped at 12 cards via `ENTER_ANIM_LIMIT`.
- New-item highlight is a **shimmer sweep**: a blurred accent band (`filter: blur(5px)`) translating `x: -120% → 250%` in 1.4s, triggered on first panel open after a capture. Played-once marks live in **module-level state** (`flashedCaptures`, keyed `itemId:capturedAt`, 60s TTL) — unpin (card moves pinned↔recent list) and view switches remount the card, and a per-instance ref would replay the sweep while the capture is still inside the 4s window (user-reported bug). Copy-button clicks suppress the sweep via a module-level `suppressFlashUntil` window (ripple already communicates the copy); the capture is still marked as flashed so reopening never re-flashes.
- Copy ripple is Material-style: it starts at the clicked button's coordinates (`getBoundingClientRect` delta from the card) and expands `scale: 0 → 15` (28px circle → ~420px, covers any card) inside a `borderRadius: 16, overflow: hidden` clip, 0.65s. `rippleOrigin` is a state set in `onCopy`, so it survives `copied` reset.
- Copy ripple final tuning (user-directed): `scale 0 → 28` (784px diameter covers the widest card incl. the left edge), **scale and opacity on separate curves** (scale 0.7s fast-fill with `[0.16,1,0.3,1]`, opacity 0.9→0 over a full 1.3s — the fade no longer collapses with the scale), radial-gradient end stops 55%/80% → **60%/100%**, `rippleEpoch` key forces replay on every click (the `copied` flag being already true stopped a re-render, swallowing rapid repeat clicks), copied resets at 1000ms.
- App icon prewarm (user-corrected strategy): **window-driven** — 1.5s after startup `prewarmAppIcons(snapshotWindows())` extracts icons for every app with a live window (not all candidate paths); the event bus increments extraction whenever a window gains foreground / becomes a copy source (`exePath` presence). `resolve` dedupes in-flight per path (prewarm and events race on new apps), disk cache (`app-icons.json`, userData, 7d TTL, 800ms debounced atomic write; negative entries never persist), seed before `initState`, negative cache 30min TTL so re-installed apps get re-probed.
- Alt+Tab switcher TabTab rework (2026-08-14): Enter-while-armed pins the session (`pinned` hook state; Alt-up is swallowed — no switch — and every other key passes through to the panel). Keyboard responsibilities split: the **hook only** owns "Alt-up doesn't execute" + keydown session-touch; Enter/Esc/arrows are handled by the renderer search input (Enter → existing `switcherClick`, Esc → new `switcher:cancel`, arrows move the filtered list and sync main via `switcherHover`). Esc = full session cancel (unpin → armed has no Alt to cycle → would hang to the 30s timeout; resetSession is cleaner). Window grouping keeps the ungrouped `windows[]` as ground truth; DTO rows carry `index` (original z-order), `groupCount` + `windows` sub-DTOs; advance moves across visible rows, hover/click report the original index and main maps back. Grouped-row click drills into a local sub-list (Back button is rendered even when unpinned — the search bar only appears when pinned). Switcher page transition: Panel `AnimatePresence` **sync mode** (not `wait` — waiting 0.1s for main's exit before mounting the switcher made Alt+Tab feel slow); rows slide in `x: 28px → 0`, 0.16s, 0.02s stagger; exit is pure 0.1s opacity fade.
- **Switcher search focus (2026-08-14, user-reported "input won't type", FOUR root causes + platform reality)**: the panel is a non-activated NOACTIVATE window for the whole switcher session, and an inactive document makes Chromium silently drop `element.focus()` — no focusin fires, so the t21 focusin→`ui:input-focus` activation bridge can never start, and the OS routes keys only to the foreground window anyway. autoFocus on the search field silently failed. Fixes: ① `switcherPin()` calls `requestPanelFocus()` (strip NOACTIVATE + `win.focus()`); ② the hook's pinned branch swallows Tab up AND down (passing Tab repeats through makes the OS see a live Alt+Tab combo and switches the foreground away); ③ pinned Alt-up sends a synthetic Alt-up so the OS Alt state isn't left held; ④ **programmatic activation of the Electron panel is refused in practice — AttachThreadInput + SetForegroundWindow works for normal app windows (execute path) but not the layered panel, even deferred past Alt-up's menu-mode cleanup. The only activation that works is a real click** (click grants input rights → WM_MOUSEACTIVATE → full Chromium activation chain), so `activatePanel` falls back to a **simulated click on the search field** (SetCursorPos + mouse_event, cursor restored <100ms later, coordinates via `screen.dipToScreenPoint`). ⑤ **Control keys (Enter/Esc/arrows) no longer depend on window activation at all**: the hook swallows them while pinned and delivers them over IPC (`switcher:control-key`); Esc cancels in main outright, enter/up/down are resolved in the renderer (drill vs execute). Only character input (IME) still needs the activated window — the simulated click provides it. Renderer keeps re-arming the bridge + retrying focus every 40ms with no try cap; `switcherTouch` self-heals on keydown while unfocused.
- **Type-to-search + search-mode Enter (2026-08-14, user request)**: while armed, any printable key (US layout: letters/digits/space/symbol rows; shift honored via `getAsyncKeyState`) pins the session and seeds the search field with that first character — the key is swallowed and the character rides in the `switcher:pin` payload (the panel isn't focused yet, so passing it through would deliver it to the window in front). Enter in search mode mirrors a mouse click: grouped rows drill into their window list (user picks one specific window), single rows switch — previously Enter always switched, which was wrong for groups.
- **Drill selection semantics (2026-08-14, user: "highlight doesn't follow my keys/mouse")**: main used to track only row-level selection (`selectedRow`), so hovering a drill sub-window changed nothing visible and execute always activated the group's first window. Now `selectedWin` (z-order index into `windows`) is the exact window: hover/click inside a drill set it, advance sets the row's first window, execute activates `windows[selectedWin]`. The renderer's drill highlight is local state (`drillSel`) initialized from the group row's first window — hover updates it instantly (no IPC round-trip) and syncs main via `switcherHover`. Drill keyboard nav lives on a window-level keydown (the search input isn't mounted in drill): arrows move + sync, Enter executes the highlighted window, Esc cancels the session.
- **Switcher keyboard ownership split (2026-08-14, final architecture)**: the hook owns ALL of pinned-mode keyboard: Tab swallowed; Enter/Esc/arrows swallowed and delivered as `switcher:control-key` (Esc cancels in main, the rest resolve in the renderer — drill vs execute depends on local state); printable keys pass through to the activated panel input for IME-compatible typing. The renderer search input has NO keydown handler anymore — the input is purely a text field; seed query, arrow moves, Enter and Esc all arrive via IPC (`switcher:pin` payload / `switcher:control-key`). This makes Enter→drill, Esc→cancel and arrow navigation work even when the window activation failed (previously these silently vanished into the foreground app).
- **Switcher click-outside cancel (2026-08-14, user: "clicking elsewhere can't dismiss, search is a dead end")**: `mainWindow.on('blur')` bound once at first show — during a session (pinned search mode holds the foreground via activateHwnd) clicking any other window blurs the panel and cancels the session exactly like Esc. Safe because: the panel has NOACTIVATE and no focus outside sessions (blur can't fire from idle), `switcherExecute` clears `active` before activating the target (no false cancel), and `releasePanelFocus` is a no-op (t21) so in-panel clicks never blur. Cancel paths are now: Esc (search input), click-anywhere-else (blur), 30s timeout (self-heal).
